## Step 7 — the depth buckets reconcile

The module buckets partition every device in the window, so they must sum to
`devices_total`. The subject buckets partition the same population separately,
so they must also sum to it.

```sql
with x as (select dash_exit_agg(now() - interval '30 days', now()) as j)
select
  (j->'depth'->>'devices_total')::int as total,
  (j->'depth'->>'devices_one_module')::int
    + (j->'depth'->>'devices_two_to_three_modules')::int
    + (j->'depth'->>'devices_four_plus_modules')::int as module_buckets_sum,
  (j->'depth'->>'devices_one_subject')::int
    + (j->'depth'->>'devices_multi_subject')::int as subject_buckets_sum
from x;
```

Expected: `module_buckets_sum = total` **and** `subject_buckets_sum = total`.

A mismatch means a device fell outside every bucket — which for the module
buckets would mean `modules_opened` was 0 or negative, impossible by
construction, and therefore a real defect rather than a data quirk.

Result: ☐ not yet run — module sum equals total: ☐ yes ☐ NO — subject sum equals total: ☐ yes ☐ NO

## Step 8 — `total_groups` is not just the row count

This is the failure this shape exists to prevent: a `total_groups` computed off
the **capped** query always equals the number of rows returned, so a truncated
list reports itself as complete and the reader never learns anything was cut.

```sql
with x as (select dash_exit_agg(now() - interval '90 days', now(), 3) as j)
select
  json_array_length(j->'exit_modules'->'rows')   as rows_returned,
  (j->'exit_modules'->>'total_groups')::int      as total_groups
from x;
```

Called with `p_limit = 3`, so `rows_returned` should be **at most 3**.

Expected: if your product has more than three distinct exit modules in 90 days,
`total_groups` is **strictly greater** than `rows_returned`. If the two are
equal here, either you genuinely have three or fewer exit modules — check with
the query below — or the cap has leaked into the count and the fix is defeated.

```sql
-- the honest uncapped group count, to tell those two cases apart
select count(*) from (
  select distinct on (e.device_id) e.device_id, e.module_id
  from events e
  where e.event_type = 'module_open' and e.module_id is not null
    and e.created_at >= now() - interval '90 days'
  order by e.device_id, e.created_at desc
) lm join modules m on m.id = lm.module_id;
```

## What this function cannot tell you

Worth writing down, because the numbers invite the wrong conclusion.

It reports **where** devices stopped, never **why**. A module at the top of
`exit_modules` may be badly written, may be where the paywall lands, may simply
be the last module in a popular subject, or may be where the semester ended.
The exit point narrows the question; it does not answer it.

`last_module` is the last module **inside the window**, not the last ever. A
device that stopped before `p_since` does not appear at all, and one still
active today appears with whatever it touched most recently — which is not an
exit. Read the tail of a wide window, not the whole of a narrow one.
