### How the parallel wave went

Tasks 7, 8 and 11 write disjoint file sets, so all three implementers ran concurrently in
one worktree. That worked, with one rule that made it safe: **implementers were forbidden
to `git add` or commit**, and the controller committed each task sequentially afterward.
Without that, one agent's `git add -A` sweeps another's half-finished files into its
commit and the review ranges become meaningless. Reviews parallelise freely — they only
write their own report files.

Tasks **9 → 10 → 12 are a genuine chain** and cannot be parallelised: the collector
defines the JSON the agent reads, and the agent's name is what the routing table wires.

**The permission check in each checklist is the highest-stakes step.** It confirms the

volumes, conversion, attribution, and cohort sizes. Do not skip it because the other steps
went green. Run it for **every** function in a migration even if an earlier statement
errored: a function created without its revoke is the one outcome the rest of the
checklist cannot detect (see §6).

## 5. Decisions already made — do not re-litigate

Everything in `HANDOFF-2026-08-05.md` §4 still holds. Rulings from these two sessions:

1. **`phaseForRange` scans, it does not sample endpoints.** The plan originally specified
   sampling the two range endpoints, which silently missed a term window enclosed by the
   range and touching neither end. The owner ruled the scanning version governs; the plan
   file was updated to match. Took three fix rounds — two of which introduced adjacent
   bugs in the same function. See the ledger.
2. **`events_type_created_idx` lives in Task 7's migration, not Task 6's.** Review found
   it served none of `growth_funnel_agg`'s queries: that function filters only on
   `created_at`, and `event_type` appears in aggregate `FILTER` clauses, which restrict
   aggregation rather than the scan. It was removed from Task 6 on the owner's ruling and
   created in `20260808000002` instead, whose `enters` CTE genuinely needs it — verified
   independently at review. **Task 7's migration is its sole creator.** Task 8's
   `growth_content_agg.opens` CTE is a second consumer and creates nothing.
3. **Migrations are written but never applied by an agent.** Applying schema to production
   is the owner's action. Implementers are scoped to write the `.sql` and the `.test.md`,
   and are told explicitly not to touch the database.
4. **`SKILL.md` is edited once, centrally, by Growth's Task 12.** All three plans depend on
   it; the Finance and Security plans were written to leave it alone and note the
   dependency instead. `package.json` gains `report:growth` in Task 9 and nothing else.
5. **The council goes live at Growth.** It needs two or more departments reporting in the
   same invocation. `SKILL.md` currently says there is no council — Task 12 rewrites that.
6. **Two rulings from 2026-08-10 that change the RPC JSON shape. Read before Task 9.**
   - **Subject-level paid counts are renamed, not recomputed.**
     `growth_segment_agg`'s `by_subject.paid_devices` filters `payments.subject_id = s.id`,
     which can never match a whole-year-plan payment, because those carry
     `subject_id IS NULL`. Year-plan payers were therefore invisible in every subject's
     count. The owner ruled the key is renamed to **`subject_plan_paid_devices`** and the
     arithmetic left alone: year-plan payers are already counted correctly in
     `by_year.paid_devices`, and spreading one payment across every subject in a year
     would inflate per-subject conversion into a meaningless number. **The gap between
     the sum of `subject_plan_paid_devices` and `by_year.paid_devices` is the year-plan
     population, not a bug** — VANTAGE must be told this so it never reports the gap as a
     discrepancy.
   - **Capped distributions carry a total count.** Several distributions are capped
     (`limit 15`, `limit 20`, `limit 25`) with no signal of how much was cut, so a
     consumer would present a truncated list as complete. The owner ruled the caps stay
     and each capped distribution gains an untruncated group count, so the interpreter can
     say "top 25 of N". The approved shape nests the list:
     `'by_subject': { 'rows': [...], 'total_groups': N }`. This applies to every capped
     distribution in `20260808000002` and `20260808000003`, and **not** to `by_year`,
     which is uncapped. **Task 9 must consume the nested form — do not write it against
     flat arrays.**
7. **The admin funnel guard test scans `lib/` as well as `app/` and `components/`.**
   Task 11's brief specified only the first two, which made the brief's own success
   criterion unreachable: `section_view` is emitted through `lib/analytics.ts`'s
   `logSectionView` wrapper, never directly from a component, so the test as written
   failed against correct code. The widening was verified not to make the dead event types
   look "emitted" — the only `lib/` matches are doc comments, a type union, and negative
   test assertions. Adjudicated by the controller, not escalated: the brief contradicted
   itself and there was only one direction to resolve it.

## 6. Things that will bite you

Everything in `HANDOFF-2026-08-05.md` §6 still applies. From these two sessions:

- **Agent definitions load at session start.** After `vantage.md` / `ledger.md` /
  `warden.md` are written, a dispatch in the same session runs a stale definition.
  **Restart the session before the first real run of any new department agent.** This
  already cost one verification run.
- **A multi-function migration whose `revoke`s are all at the end has a real exposure
  window.** Postgres default-grants `EXECUTE` on a new function to `PUBLIC`. If the SQL
  editor does not apply a paste atomically, a statement that errors partway through leaves
  the already-created functions **unrevoked and readable by anyone holding the public anon
  key** — and the checklist's anon check cannot distinguish "the revoke worked" from "the
  function was never created." The fix adopted in Task 8: each `revoke`/`grant` pair sits
  immediately after its own `create or replace function`. Do this in every future
  multi-function migration rather than trusting the editor's transaction semantics.
- **`tsconfig.json` targets ES2017, which rejects the regex `s` (dotAll) flag** with
  TS1501. The Growth plan hit this once at line 1027; the fix was a `RegExp` constructor
  with the same pattern and flag.
- **Verification docs are the only record of what "passing" means**, since nobody can
  execute them here. **A doc that explains away a symptom is worse than no doc.** Task 6's
  first draft told the owner a persistent Seq Scan "is not itself a failure" and blamed
  table size — which would have permanently masked a dead index. Reviewers must read
  these as deliverables, not as prose.
- **Regression tests that pass against the code they guard protect nothing.** This was the
  recurring defect across Task 3's three rounds. The way to settle it is to make the
  reviewer revert the fix and watch the test fail. Task 11's reviewer did exactly that —
  backed the file up, restored the buggy list, confirmed the guard failed with the dead
  types named in the message, then restored and confirmed a clean `git status`. **Ask for
  that explicitly, and ask for the failure output.**
- **Never let parallel implementers stage or commit.** Disjoint file sets make concurrent
  *writes* safe, but a shared git index does not parallelise: one `git add -A` pulls
  another agent's in-progress files into the wrong commit and every review range downstream
  is wrong. Implementers write; the controller commits sequentially.
- **A brief can be internally contradictory, and the implementer is the one who finds
  out.** Task 11's brief mandated a scan scope that made its own stated pass bar
  unreachable. Both of the wave's SQL implementers were told to verify every schema claim
  by grepping rather than trusting the brief, and both found real things that way. Keep
  that instruction in every dispatch.
- **Session limits will interrupt long agent dispatches.** They hit five times over this
  build. Instruct plan-writing and long-form agents to **append each completed section to
  disk as they go** rather than composing everything and writing once at the end.
- **`.claude/settings.local.json` sets `defaultMode: acceptEdits`** with a broad prefix
  allowlist and a deny list covering `rm -rf`, `sudo`, force-push, `git reset --hard`,
  `vercel rm`, `supabase db reset`, and `npm publish`. It does **not** deny
  `git filter-branch`.

## 7. Real defects found while planning and building

These are independent of the department build; the build only surfaced them.

### 7.1 Semester plan stops being worth anything on 2026-11-30

`lib/paymongo.ts:36-40`. `periodEndFor` floors semester plans at 31 days so a stale
constant can never grant less than a month. But once `from` passes `SEMESTER_END - 31
days`, the semester branch falls through to the same `monthEnd` that `subject_month`
returns — identical access, for the more expensive plan. `SEMESTER_END` is bumped by hand
("Bump once per semester when the selling window rolls over"), so a missed bump makes this
permanent and silent. Both list prices are public in `lib/paymongo.ts`. **Not yet fixed.**

### 7.2 Live database has drifted from the migrations

Seven RPCs are called by application code and defined by **no migration**:
`admin_funnel_counts`, `admin_dau_30d`, `admin_active_since`, `admin_user_totals` (all
from `app/admin/page.tsx`), and `check_login_lockout`, `record_login_attempt`,
`clear_login_attempts` (all from `app/api/admin/login/route.ts` — these gate **admin login
lockout**). Three siblings do have migrations, so the drift is partial. Also
`waitlist.year_label`, `subject_title`, `module_title` are written by
`app/api/waitlist/route.ts` and created by no migration.

Task 8's implementer confirmed this independently from the other direction: the shipped
`admin_waitlist_agg()` already **reads** `waitlist.year_label` and `subject_title`, so
those columns exist in production and in no migration file. Its verification doc handles
the uncertainty with a discriminating fallback rather than assuming.

`supabase/migrations/20260719010000_api_rate_limits.sql:2` acknowledges the drift in a
comment ("Modeled on the live login_attempts pattern"). **The database cannot be rebuilt
from its migrations today.** This belongs to Operations' data-ops sub-function.

### 7.3 The admin dashboard renders an unmeasured step as a real zero

`app/admin/page.tsx:137` resolves a missing event type with
`funnelCounts.get(step.type) ?? 0`, so a step the data source returned nothing for is
indistinguishable on the page from a step that genuinely had no activity. This is
pre-existing and unchanged by Task 11, but Task 11 newly routes three paywall steps
through it, which makes it consequential — and it contradicts the plan's own standing rule
that an unmeasured value is `null` and renders as `not read`, never a number.

**Two owner actions here, both cheap:**

1. **Check that `admin_funnel_counts` returns rows for `paywall_teaser_view`,
   `paywall_teaser_click` and `subscribe_click`.** That RPC is one of the seven in §7.2 —
   it exists only in production, so nothing in this repo can answer it. If it does not
   return those types, Task 11 traded two frozen counters for three that read `0` forever,
   which is worse, because zero looks like data. The check is read-only and is written out
   in `.superpowers/sdd/2026-08-08-growth-department-agent/task-11-review.md`.
2. **Decide what the dashboard should render for an unmeasured step.** Fixing `?? 0`
   properly changes `AdminDashboard`'s props contract, which is why it was escalated
   rather than patched inside Task 11.

### 7.4 Finance planning found three ledger defects

Detailed in the Finance plan's own "What could not be verified" section:
`recordPayment` overwrites `subscriptions.paymongo_link_id` on renewal (a naive link-id
join would report a **false P0** every month); the `SEMESTER_END` parity above; and an
untransacted webhook path at `app/api/webhooks/paymongo/route.ts:135-178` that inserts the
payment row then the class row with no rollback, so a class-insert failure returns 500
with money recorded and nothing granted.

### 7.5 Security planning found real issues, deliberately not described here

Three findings and one cross-layer observation, named by file only:
`supabase/migrations/20260623_enable_rls.sql`; `lib/deleteAccount.ts` together with the
identity columns declared across `supabase/migrations/`; `package-lock.json`; and a
cross-layer observation spanning `lib/auth/adminSession.ts` and `middleware.ts`.

**Details are withheld from this tracked file on purpose.** A plan or handoff that says
"here is the check, and here is what it found" is a disclosure with a permanent URL. All
four fall inside checks the WARDEN plan builds (Tasks 3, 4, 5, 7) and will surface on the
first private run into `docs/reports/security/`, which is gitignored. Do not go looking

### Dispatch shape that worked

Give each implementer: one line on where the task fits, the brief path as its single
source of requirements, interfaces from earlier tasks it cannot know, the binding global
constraints, and the report-file path. **Never make a subagent read the whole plan.** Then
generate a review package and dispatch a separate reviewer for spec compliance *and*
quality — the implementer's self-review does not replace it.

Ask reviewers to **verify by execution, not by reading**. Every finding that mattered in
this build came from a reviewer that ran something. For a task that cannot be executed
here — a migration — that means grepping every schema claim against the migrations and the
app code rather than trusting the brief. Both SQL implementers and both SQL reviewers found
real defects that way.

**Tell every implementer which findings are *not* theirs.** Each fix dispatch in this
session listed the deferred minors and the escalated items by name and said "do not fix
these." Without that, a fix round quietly grows into a refactor.

## 10. Working conventions

- Commits: conventional-commit prefixes, **no trailer block ever**, no `Co-Authored-By`.
  The owner is the sole contributor. See `CLAUDE.md`.
- Tests colocate as `<name>.test.ts`.
- Migrations get a `<name>.test.md` verification doc — a real Postgres run, not an assertion.
- No new npm dependencies without a reason.
- Manila dates everywhere (`Asia/Manila`), half-open windows (`>= since`, `< until`).
- Aggregate in Postgres, never in JavaScript — Supabase caps a `select` at 1000 rows.
- `docs/reports/` is gitignored in full and stays that way.
- `superpowers:brainstorming` before creative work, `writing-plans` for plans,
  `subagent-driven-development` to execute them.
